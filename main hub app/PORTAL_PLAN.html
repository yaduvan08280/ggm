3Architecture

The hub is the only user list and password store. Each of the 5 apps gets one small, identical file, the Portal Connector, that trusts messages signed by the hub. The 3 public dashboards are only tiles.

The Portal Connector (one file added to each of the 5 apps)

Entry pointCalled byWhat it does
doGet(e) with ?pt=Browser (iframe inside the hub)Checks the signature, expiry, app ID and single use. Creates the app's own normal session and serves the page with it filled in, so no login screen appears. Works in both switch positions.
doGet(e) without a passSomeone opening the old linkSwitch ON: shows "Open through GGM Portal". Switch OFF: shows the app's login form, which now asks for the portal username/phone + password (checked by the hub, see below).
doPost op:"meta"Hub, daily and from a menu itemReturns the app's roles, sites and (Staff Dashboard) doer names, for the dropdowns.
doPost op:"provision" / "disable"Hub sync queueCreates, updates or switches off one user using the app's own rules, and removes the sessions of switched-off users. Never deletes rows.
doPost op:"mode"Hub, when an admin flips the switchStores PORTAL_ONLY = true/false in the app's Script Properties. Turning it ON also ends sessions that were started outside the portal.
doPost op:"counts"Hub trigger, every 5 minReturns {localId: pendingCount} for all users with access, using the app's own logic.

Indent Flow already has a doPost for Telegram. The connector adds a branch checked by e.parameter.portal, so the Telegram webhook is untouched.

The Portal-only switch

  OFF: "apps open separately"
  • Each app's own link works on its own, as today.
  • Its login form asks for the same portal username or phone + password. The app sends them to the hub (signed server-to-server call op:"verify"), and the hub checks the password and the Access tick. There are no separate app passwords to keep in step.
  • The portal still works too, with no login inside apps.
  ON: "portal only"
  • Opening any app's link directly shows "Open through GGM Portal" with a button to HUB_URL?app=ID.
  • App login forms are switched off. The only way in is a launch pass from the hub.
  • Sessions started outside the portal end the moment it's turned ON.
  • Who can flip it: only users ticked Portal Admin in the Users tab. They see an extra Admin item in their account menu (mockup in section 7).
  • What happens on flip: the hub saves the new state, pushes op:"mode" to all 5 apps in parallel, and shows ✓/✗ per app. A failed app is retried every minute until it confirms. Each flip is logged (MODE_ON / MODE_OFF, by whom).
  • Emergency: if the hub itself is broken while the switch is ON, itadmin@ can set PORTAL_ONLY=false directly in any app's Script Properties to reopen that one app.
  • Not affected: the 3 public dashboards (they stay open links either way).

4How each requirement is met

① Master user list creates the user in every app

1
Admin adds a row to Users (username, name, phone, email, active ✓).
2
Admin ticks apps in Access and picks role, site or doer name where needed. The existing onPortalEdit trigger queues the change in Sync.
3
A 1-minute trigger (or menu → Sync now) sends provision to each app, which writes the user in its own format:
AppWhat gets written into the appMust not break
Indent FlowUsers row through the app's own saveUser_ rules: User_ID = username in capitals, Name, Role, Site (USER/STORE: chosen site; others ALL), Phone, Email, Active. PIN = random (the app's own PIN is no longer used).Updates never touch Telegram_* or Language.
Fuel & Car TasksFills the auth columns only (EMAIL, NAME, STATUS) in the first row whose EMAIL is empty. EMAIL = the portal email, or the username if the person has no email (it's only a lookup key now). PASSWORD = hash of a random value.Cols A–B (Driver and Vehicle lists) are never touched. A blank PASSWORD would mean the password is 1234, so it is never left blank.
GGM AssetsNothing in the sheet. Role (SITE/BOSS) and site travel in the pass and sit in the server session.The old site logins in Users stop being used once connected.
Staff DashboardNew staff: a row in Doer List (mobile, exact full name) and Users (mobile, random password, name). Existing staff are only mapped to their existing Doer List name.Task sheets find people by name, so the exact Doer List spelling is used.
Main Admin DashboardNothing (no user list). Access is the tick.n/a

② Roles and sites from each app, as dropdowns

  • Indent Flow: Role ADMIN / STORE / PURCHASE / PC / USER. Site = active sites from its Sites tab. USER and STORE need a site; other roles are locked to ALL.
  • Fuel & Car Tasks: tick only.
  • GGM Assets: Role SITE / BOSS. Site = the 6 from LOCATION_BLOCKS. SITE needs a site; BOSS sees all.
  • Staff Dashboard: Doer name dropdown, sourced from Doer List.
  • Main Admin Dashboard · Mines · Collection · Levanto: tick only.

Lists are refreshed daily from each app's meta into a hidden Lists tab. Conditional formatting greys out unticked columns and marks missing required values in red. Red rows don't sync.

③ Assign apps with a tick and a dropdown

The Access grid gets a two-row header: the app name across its columns, with ✓ / Role / Site underneath. See section 6.

④ Pending tasks as a dot on each tile

  • A 5-minute trigger calls counts on the 5 apps in parallel (one call per app for all users) and reads Levanto's sheet for its alert count.
  • Results are cached. getHome() adds a badge to each tile, so the home screen isn't slowed down.
  • When someone closes an app, the hub refreshes that app's count for that person, so finished work clears straight away.

⑤ Log in once, never again inside apps

1
Tile tap → launchApp() checks access again → returns APP_URL?pt=<pass> (username, name, local ID, role, site, unique ID, 90 s expiry).
2
The app's doGet checks the pass, creates its own normal session, and serves the page with PORTAL_BOOT = {token, user}.
3
The page skips its login screen. Every screen works unchanged because the session is the same kind the app always used.
4
Old links opened directly follow the Portal-only switch (section 3).

⑥ Password reset by email OTP

1
Login → Forgot password? → username or phone → the hub shows the email masked (r•••••@ggminerals.com).
2
A 6-digit code is emailed. Only its hash is kept, for 10 minutes. 5 wrong tries kills the code, 60 s between resends, max 5 per hour.
3
Code + new password (twice) → new salt and hash. All other devices are signed out automatically. Logged as PASSWORD_RESET.
4
First-time users use the same screen, so no password is ever typed into the sheet. People without email get a temporary password from the admin.

One password covers everything: the portal, and each app's own login form while the switch is OFF. The apps' old password and OTP screens (Fuel has one) are hidden.

5Changes you asked for inside the apps

Small, targeted changes. The workflows stay the same.

Fuel & Car Tasks: "who filled" = logged-in user

  • Form: the f_driver dropdown is replaced by a locked field showing the logged-in user.
  • Server: submitFuelForm ignores whatever the browser sends for driver and writes the username from the session into column B of FUEL DETAIL DRIVERS. Column I keeps the login identity as today. Other columns are unchanged.
  • Service form (confirmed): the same rule. s_driver is removed, and submitServiceForm writes the session username into column B of SERVICE COST.
  • Mileage and cost-per-km maths group by vehicle, so they are unaffected.

Main Admin Dashboard: every action stamped with the username

  • New task: "Given By" (today a hand-picked dropdown) becomes the logged-in admin's username, set on the server. "Assign to" lists all portal users who have the Staff Dashboard ticked (from the hub, so switched-off people vanish). It writes that person's exact doer name into column C, which the Staff Dashboard needs to find the task.
  • Every write records who did it (addNewTask, editTask, updateTaskStatusById, rejectTaskByBoss, leave decisions, renewal actions, routine "mark done"). They go in new columns on the right of each sheet:

GGM Assets: people log in, sites are assigned

  • Each person logs in as themselves. Their role (SITE/BOSS) and site come from the Access grid and are held in the server session, not in localStorage.
  • Transfer and Receive rows: column B (today "TONK (Web UI)" or a Google email) records the username. Source and destination site columns are unchanged, and so are the sync logic and the Present Assets grid.
  • Every server function checks the session. A SITE user can only act for their own site on the server, not just in the page.

Staff Dashboard (staff app)

  • The session carries the exact Doer List name, so the app stops guessing people from name fragments.
  • Staff actions (mark done, remarks, transfer requests, self tasks, leave requests) keep writing names where they do today. The same "Done By" username columns above can be filled here too, which is recommended so the audit trail is complete.
